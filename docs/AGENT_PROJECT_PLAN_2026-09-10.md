# LangGraph 多 Agent RAG 项目规划

## 项目定位

截止目标：2026-09-15 周二晚上完成可演示版本。

本项目基于开源项目 `ro-anderson/multi-agent-rag-customer-support` 二次改造，不直接沿用原始旅游客服业务，而是改造成贴合个人实习经历的业务场景：

```text
品牌社媒洞察与周报支持多 Agent 系统
```

项目核心不是“部署一个开源 Demo”，而是展示如何把品牌监测、VOC 口径、自动化周报、数据下钻等实习经历抽象成一个可交互的多 Agent RAG 系统。

## 业务背景

在品牌社媒监测和自动化报告场景中，业务方常见问题包括：

- 某品牌本周声量、互动、情绪表现如何。
- 哪些平台或内容类型带来主要变化。
- 用户负向反馈集中在哪些场景和标签。
- 周报指标口径、对比周期、竞品池、关键词过滤规则如何解释。
- 当报告结果异常时，如何定位是数据源、口径、过滤词还是生成链路问题。

原始项目的“旅游客服多 Agent”可以改造成“品牌洞察支持多 Agent”：

| 原始角色 | 改造后角色 | 负责内容 |
| --- | --- | --- |
| Primary Assistant | 主路由助手 | 判断用户意图，路由到具体业务 Agent |
| Flight Assistant | 周报指标 Agent | 解释 SOV、SOE、NSR、环比、同比、平台拆解 |
| Hotel Assistant | VOC 洞察 Agent | 分析场景、维度、标签、情绪和原帖下钻 |
| Car Rental Assistant | 数据质量 Agent | 检查噪音、过滤词、品牌识别、异常归因 |
| Excursion Assistant | 行动建议 Agent | 基于洞察输出运营建议、内容建议和复盘摘要 |

## 技术目标

最小可演示版本需要覆盖：

- LangGraph 状态图：用节点和条件边组织多 Agent 流程。
- RAG 知识库：把项目说明、指标口径、模拟社媒数据、周报片段向量化。
- Qdrant 向量库：存储切片后的 embedding，支持语义检索。
- 工具调用：按不同 Agent 暴露不同查询工具。
- 安全分层：只读查询属于 safe tool，生成报告、改配置等动作设计成 sensitive tool，需要确认。
- 记忆与状态：保留当前对话上下文，支持多轮追问。
- 可观测性：接入 LangSmith 或输出本地日志，用于复盘 Agent 路由与工具调用。

## 数据设计

公开演示只使用模拟数据和脱敏材料。

推荐准备 4 类数据：

1. 指标口径文档
   - SOV、SOE、NSR、互动量、声量、情绪等定义。
   - 周期对齐、竞品池、平台范围、过滤词规则。

2. 项目知识文档
   - 海信自动化周报项目复盘。
   - 雅迪 VOC 社媒洞察项目复盘。
   - Haier GEO 链路验证的简化说明。

3. 模拟结构化数据
   - 品牌、平台、发布时间、内容类型、声量、互动量、情绪、标签、场景。
   - 控制在几百到几千条即可，重点是结构清楚，不追求真实规模。

4. 样例报告片段
   - 本周概览。
   - 竞品对比。
   - VOC 负向场景。
   - 异常归因。
   - 行动建议。

## 切片策略

面试时需要讲清楚“为什么切、怎么切、怎么验证”。

为什么要切：

- 原文档太长，不能整篇塞进模型上下文。
- 检索需要定位到相关段落，而不是把无关内容一起传给模型。
- 切片后可以降低 token 成本，并减少模型被噪音干扰。

怎么切：

- 指标口径文档：按指标或规则切，每个切片保留完整定义、计算方式、注意事项。
- 项目复盘文档：按“背景、目标、流程、结果、复盘”切。
- 样例报告：按一级标题和自然段切，保留品牌、周期、平台等上下文元信息。
- 模拟原帖数据：一条或几条记录为一个切片，元信息保留品牌、平台、情绪、场景、标签。

建议参数：

```text
chunk_size: 500-800 中文字符
chunk_overlap: 80-120 中文字符
metadata: brand / platform / date_range / doc_type / project / section
```

为什么要 overlap：

- 防止定义、原因、结论被切在两个片段里。
- 对“本期变化原因是什么”这类问题，模型需要同时看到数据变化和解释文本。

## 系统架构

本地演示架构：

```text
文档 / CSV / Markdown
↓
清洗与切片脚本
↓
Embedding 生成
↓
Qdrant 向量库
↓
LangGraph 主状态图
↓
主路由助手
↓
周报指标 Agent / VOC 洞察 Agent / 数据质量 Agent / 行动建议 Agent
↓
工具调用 + RAG 召回
↓
回答、复盘、建议
```

## 面试讲法

一句话介绍：

```text
我基于 LangGraph 改造了一个多 Agent RAG 系统，把实习中做过的品牌社媒监测、VOC 分析和自动化周报场景抽象成多个专业 Agent，由主路由助手判断问题类型，再调用不同工具和知识库完成指标解释、洞察分析、异常排查和行动建议。
```

技术亮点：

- 用 LangGraph 显式编排 Agent 状态图，而不是只写单轮 Prompt。
- 把业务问题拆成多个专职 Agent，降低单 Agent 指令膨胀。
- 用 RAG 解决指标口径、项目资料、样例报告的长期知识注入问题。
- 用元数据过滤提升召回精度，避免不同品牌、平台、文档类型混召。
- 把 sensitive tool 和 safe tool 分开，展示对真实业务操作风险的控制意识。

可以展开的复盘点：

- 数据为什么要清洗和切片。
- 不同文档类型为什么采用不同切片策略。
- chunk size 和 overlap 如何影响召回。
- 多 Agent 相比单 Agent 的优势和代价。
- RAG 失败时如何排查：切片、embedding、召回、prompt、路由、数据质量。
